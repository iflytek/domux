## 📌 摘要（TL;DR）

本报告回答一个问题：**我们用 SFT + GRPO 训练 Domux，效果好的原因到底是什么？** 结论建立在训练日志（SwanLab）和测试集逐样本对比之上，不依赖事后编造的叙事。

一句话概括：

> **SFT 已经完成了绝大部分能力获取，把模型推到了接近天花板的水平；GRPO 不是在"学新东西"，而是在 SFT 留下的长尾上做针对性精修——把表层说法收敛到唯一规范形、抑制凭空填充的槽位。增益虽小但方向明确，且代价可诊断。**

关键事实速览（数据来自 6733 条测试样本的配对分析，可由 [复现说明](#-复现说明) 重跑）：

| 维度 | SFT | SFT+GRPO | 变化 |
| --- | --- | --- | --- |
| 整句精确匹配率（EM） | 86.54% | 87.20% | **+0.65 pp** |
| 平均字段准确率 | 97.23% | 97.67% | **+0.44 pp** |
| GRPO 修好的样本 | — | — | **53 条** |
| GRPO 弄坏的样本 | — | — | **9 条** |
| 修复 : 破坏 | — | — | **≈ 5.9 : 1** |
| 训练 reward（SFT 训练末期已达） | ~0.999 | — | 近饱和 |

三个值得记住的发现：

1. **训练 reward 从 GRPO 第一步就饱和在 ~0.999**——说明能力主体来自 SFT，GRPO 的工作空间在长尾。
2. **GRPO 修好的错误高度集中在"规范化"**：设备名（29 次）、房间（22 次）、动作（10 次），典型如 `Sleep Mode → Sleeping Mode`、`Light → Shower Light`、`turnOn|Relax → activate|Relax Mode`。
3. **GRPO 弄坏的 9 条全部是同一种过泛化**：把罕见的紧凑命名 `LightA` 误"规范化"成 `Light A`——它犯错的方式，恰恰证明了它学对了什么。

## 🎯 1. 引言：从工程结果回看

Domux 的训练分两步：先用带标注数据做 LoRA 监督微调（SFT），再用自定义奖励函数做 GRPO 强化学习（细节见 [`training/README.md`](../training/README.md)）。这套组合在工程上跑通了、指标也不错，但"为什么有效"一直停留在直觉层面。

本报告的目标是把"设计选择 → 训练动力学 → 可观测结果"这条因果链补齐，并且**只采信能被日志或测试数据证实的部分**。凡是数据不支持的推断，会明确标注为推测或留作未来工作，不会伪装成结论。

需要特别说明的是：我们最初的假设之一（"双奖励会形成由易到难的隐式课程"）在看到训练曲线后被**推翻**了——曲线显示两个奖励从一开始就饱和，并不存在"先学格式、再学语义"的过程。本报告保留这个修正过程，因为它本身就是"用证据约束解释"的一个例子。

> ⚠️ **数据来源声明**：本报告的测试数据来自一套**内部 family 评测集**（6733 条，按户型 fy001~fy006 分组），与本仓库 [`eval/`](../eval/) 目录下随发布提供的**官方测试集**（`smart_home_control_test_set.jsonl`，按 category 分组）是**两套不同的数据**——两者 query 几乎不重叠（交集仅 36 条）。二者的打分口径也不同：官方脚本 [`eval/run_eval.py`](../eval/run_eval.py) 报告 Result accuracy（顺序无关的集合匹配）与 Slot F1，本报告使用整句精确匹配（EM）与按字段位置统计的平均准确率。**因此本报告的数字不可与官方 eval 的指标直接横向比较。** 本报告的价值在于 SFT 与 GRPO 在**同一份数据上的逐样本配对差异**，这一比较不受口径差异影响。

## 🧱 2. 两阶段范式：SFT 是主体，GRPO 是精修

### 2.1 训练曲线说了什么

GRPO 训练过程中，两个奖励函数（`SlotAccuracy` 与 `SlotFormat`，定义见 [`training/rewards/reward_plugin_slot.py`](../training/rewards/reward_plugin_slot.py)）的均值曲线呈现出一个鲜明特征：

- **`SlotAccuracy/mean`**：从 step 0 起就在 **~0.999**，全程贴近 1.0，仅有偶发的向下尖刺（掉到 0.99~0.992）后迅速弹回。
- **`SlotFormat/mean`**：从 step 0 起就在 **~0.9998**，几乎是一条直线，偶发尖刺掉到 0.998。

> 📈 *图 1：GRPO 训练期间的奖励曲线（SwanLab）。两条曲线均在 GRPO 起点即饱和，仅有偶发的向下尖刺后迅速弹回。*

</div>

这意味着：**在 GRPO 开始之前，SFT 模型就已经把格式合规性和槽位准确率都做到了接近天花板的水平。** 因此 GRPO 阶段并不存在"能力从无到有"的学习过程，它面对的是一个已经很强的初始策略。

### 2.2 为什么这恰好证明了 SFT 是 GRPO 的前置条件

GRPO 不使用价值网络（critic），某条采样的优势完全由**组内相对得分**估计：

```
A_i = (r_i − mean(r_1..r_G)) / std(r_1..r_G)
```

这个公式有个常被忽略的前提：**组内必须存在奖励差异**。如果同一条指令的 G 条采样得分几乎都一样（reward 饱和 → 组内 std → 0），那么优势 A_i ≈ 0，这一组对梯度几乎没有贡献。

把它和曲线对起来看就通了：

- reward 近饱和 → 绝大多数 step 的组内方差很小 → 梯度很小；
- **唯一产生有效梯度的地方，正是那些向下尖刺**：采样偶尔吐出一条坏 rollout，它和组内其它好样本拉开差距，组内方差非零，GRPO 在这一步把这条坏样本的概率压下去；
- 曲线上尖刺被快速弹回 1.0，就是这个"抑制坏输出"过程的可视化。

由此得到本节的核心论点：

> **SFT 负责把策略的采样分布搬进"奖励函数能给出有效信号"的区域；GRPO 在这个区域内做精修。如果跳过 SFT 直接对基座做 GRPO，采样几乎不可能命中合法的 7 字段格式，组内全是 0 分、方差塌缩，GRPO 从第一步起就没有梯度。SFT 不是可有可无的暖身，是 GRPO 梯度非平凡的必要条件。**

### 2.3 为什么不能只靠 SFT 跑到底

既然 SFT 这么强，为什么还要 GRPO？因为 SFT 的训练目标（行为克隆，等价于最小化前向 KL）是 **mode-covering** 的：为了覆盖数据里出现过的各种说法，它倾向于把概率质量摊开，而不是在每个输入上锐化到唯一正确输出。

后果是：SFT 后的模型在**近义表层形之间仍然摇摆**——它知道大致该输出什么，但在"`set` 还是 `adjustUp`""设备名该不该规范化""该不该填 `*`"这类需要锐化决策的地方不够果断。这正是测试集上那些错误的来源，也正是 GRPO（mode-seeking，倾向锐化到高奖励的那个解）能补上的部分。下一节用逐样本数据证实这一点。

## 🔬 3. 核心证据：GRPO 修好了什么、弄坏了什么

我们把同一份测试集（6733 条，覆盖 6 个家庭布局 fy001~fy006）在 SFT 和 SFT+GRPO 两个模型上的输出**逐条配对**，统计精确匹配状态的变化。

### 3.1 配对结果：改动克制，修复远多于破坏

| 配对状态 | 样本数 |
| --- | --- |
| 两个模型都对 | 5818 |
| 两个模型都错 | 853 |
| **GRPO 修好**（SFT 错 → GRPO 对） | **53** |
| **GRPO 弄坏**（SFT 对 → GRPO 错） | **9** |
| **净增益** | **+44（+0.65 pp），修复 : 破坏 ≈ 5.9 : 1** |

两点观察：

1. **GRPO 的改动非常克制**——6733 条里只动了 62 条（约 0.9%），其余 96.8% 保持不变。这与 2.2 的"近饱和、低梯度"完全一致：它没有大改，只在边角发力。
2. **修复 : 破坏 ≈ 6 : 1**——这正是训练曲线上"尖刺被弹回"在测试集上的对应物：GRPO 在压制低频坏输出。

### 3.2 GRPO 修好的是什么类型的错误

按修复样本中 SFT 的出错字段统计（一条样本可能多个字段出错）：

| SFT 出错字段 | 修复次数 |
| --- | --- |
| device（设备名） | 29 |
| room（房间） | 22 |
| action（动作） | 10 |
| floor（楼层） | 5 |
| attribute（属性） | 2 |
| value（值） | 1 |

看几个真实例子，主题非常一致：

```
"switch the mode to sleeping"
  SFT : activate|Sleep Mode|*|*|*|*|*          ← 设备名没收敛到标准形
  GRPO: activate|Sleeping Mode|*|*|*|*|*        ← 修对

"brighten the shower light on the first floor"
  SFT : adjustUp|Light|brightness|*|*|Shower|First Floor   ← 设备拆错 + room 填了幻觉值
  GRPO: adjustUp|Shower Light|brightness|*|*|*|First Floor  ← 合并设备名 + 删掉多余 room

"set the relax in the master bedroom on the first floor"
  SFT : turnOn|Relax|*|*|*|Master Bedroom|First Floor      ← 场景模式用错 action + 设备
  GRPO: activate|Relax Mode|*|*|*|Master Bedroom|First Floor ← 修对

"set the bedside light brightness to 50 percent"
  SFT : set|Bedside Light|brightness|50|Percent|Bedroom|*  ← 凭空多填了 room
  GRPO: set|Bedside Light|brightness|50|Percent|*|*         ← 抑制幻觉槽位
```

归纳起来，GRPO 的修复集中在**两个主题**：

- **规范化（canonicalization）**：把表层说法收敛到唯一标准形——`Sleep → Sleeping Mode`、`Light → Shower Light`、场景词 `turnOn|Relax → activate|Relax Mode`。这正好对应 2.3 说的"SFT 的 mode-covering 在近义形之间摇摆，GRPO 的 mode-seeking 把它锐化"。
- **抑制幻觉槽位**：删掉 SFT 凭空补出的 `room` / `floor`（如 `set bedside light` 误填 `Bedroom`）。

## 📊 4. 字段级证据与奖励设计的呼应

### 4.1 字段级准确率

把配对数据按 7 个字段位置分别统计准确率（取段数匹配的子集，n=6724）：

| 字段 | 奖励权重 | SFT | GRPO | Δ |
| --- | --- | --- | --- | --- |
| action | 0.25 | 0.9857 | 0.9896 | +0.39 pp |
| device | 0.25 | 0.9346 | 0.9380 | +0.34 pp |
| attribute | 0.20 | 0.9881 | 0.9955 | **+0.74 pp** |
| value | 0.15 | 0.9957 | 0.9975 | +0.18 pp |
| unit | 0.05 | 1.0000 | 1.0000 | 0.00 pp |
| room | 0.08 | 0.9114 | 0.9207 | **+0.94 pp** |
| floor | 0.02 | 0.9970 | 0.9993 | +0.22 pp |

> 字段权重见 [`reward_plugin_slot.py`](../training/rewards/reward_plugin_slot.py)（`FIELD_WEIGHTS`）。

### 4.2 一个需要诚实对待的细节

直觉上会预期"奖励权重高的字段提升大"。数据**部分支持、部分不支持**这个直觉，必须如实说明：

- **device 是全局准确率最低的字段（0.93~0.94）**，也是 GRPO 修复次数最多的（29 次）。它权重高（0.25）、出错空间大，所以成为主要发力点——这一条符合直觉。
- **但 room 的字段准确率提升最大（+0.94 pp），而 room 的权重只有 0.08**。这说明 room 的修复并非由其奖励权重直接驱动，更可能是**搭着 device 的修复一起发生的**：像 `Light + Shower → Shower Light` 那个例子，把设备名合并对了，原本错填到 room 的 `Shower` 也顺势消失，device 和 room 同时变对。

换句话说，**字段级提升不能简单地用权重大小线性解释**；规范化是以"整条命令"为单位发生的，一次修复常常同时纠正多个字段。这是观察到的现象，不是设计时就预期的，如实记录于此。

## 🧭 5. 机制解释、局限与未来工作

### 5.1 GRPO 弄坏的 9 条，暴露了它的机制

最有解释价值的部分，恰恰是 GRPO 弄坏的那 9 条。它们**全部集中在 fy006**（也是唯一一个 GRPO 拉低了 EM 的布局：0.6135 → 0.6074），而且几乎是同一个错误：

```
"turn off the lighta..."   期望: turnOff|LightA|...
  SFT : turnOff|LightA|...   ← 对
  GRPO: turnOff|Light A|...  ← 把紧凑设备名拆开了
```

机制解释很清楚：

> GRPO 从训练数据里学到了一条强先验——**多词设备名要带空格**（`Strip Light`、`Shower Light`、`Spot Light`…，这也是 [`output-spec`](output-spec.zh.md) 的规范）。这条先验在绝大多数情况下是对的，正是 3.2 里大量修复的来源。但它**过度泛化**了，把 fy006 里罕见的紧凑命名 `LightA / LightC` 也"规范化"成了 `Light A / Light`。

这正是 mode-seeking（reverse-KL）策略改进的**已知代价**：收敛到主流模式时，会牺牲罕见的例外模式。值得强调的是——**GRPO 弄坏东西的方式，反过来证明了它学对了什么**：它的回退不是随机噪声，而是"把规范化规则用过了头"，这与它带来收益的机制是同一个。

### 5.2 一个必须讲清的边界：增益主要在泛化，不在训练 reward

需要诚实指出：训练 reward 早已饱和在 ~0.999（第 2 节），这既说明 SFT 已很强，也意味着**奖励函数在这个水平上已接近失去区分度**——它很难再分清"好"和"更好"。因此 GRPO 在训练分布上能榨取的空间本就有限，它的价值体现在**测试集（泛化）的长尾修复**上，而非训练指标的进一步抬升。这也解释了为什么整体增益看起来不大（EM +0.65 pp）：天花板效应下，能动的本就只有那条尾巴。

对**命令解析**这类任务而言，这条尾巴的意义被低估了：一条命令错 = 一个物理动作执行错。把 worst-case 错误压下去（修复 : 破坏 ≈ 6 : 1）的可靠性收益，比 mean 指标的小数点更值得关注。

### 5.3 一个值得留意的口径张力：训练在意顺序，评测不在意

有一个设计细节值得记下来：**奖励函数 [`reward_plugin_slot.py`](../training/rewards/reward_plugin_slot.py) 是顺序敏感的**——它用 LCS 对齐保留命令段的先后（注释明确写了 `turnOff→turnOn` 与 `turnOn→turnOff` 不同），而官方评测脚本 [`eval/run_eval.py`](../eval/run_eval.py) 的 Result accuracy 是**顺序无关的集合匹配**。也就是说，训练时模型因"段顺序错"被扣分，但评测时同样的顺序错却可能被判对。

这对当前任务影响有限（绝大多数指令的多段之间本就无强制先后），但它是一个真实的"奖励—评测"不一致点。如果未来引入对顺序敏感的指令（如"先关再开"），需要让评测口径与奖励口径对齐。本报告记录这一点，不将其作为已观测到的问题。

### 5.4 局限与未来工作

本报告的结论受限于现有数据，以下几点尚未验证，留作未来工作，**不作为已成立的结论**：

- **缺少消融实验**：未单独验证"移除 `SlotFormat` 只留 `SlotAccuracy`"对收敛的影响。因此关于两个奖励各自贡献的论断仅停留在机制推断层面。
- **字段级准确率为事后解析口径，与官方 Slot F1 不同**：本报告的字段级准确率是从配对输出**事后解析**得到的（段数匹配子集，按字段位置统计平均准确率），与官方脚本 [`eval/run_eval.py`](../eval/run_eval.py) 的 **Slot F1**（贪心对齐 + 2PR/(P+R)）在算法和口径上都不同，两者数字不可直接对比。
- **fy006 的过泛化可被针对性缓解**：例如在 SFT/GRPO 数据中加入紧凑命名样本，或在奖励里对"无依据改写设备名"加惩罚。这是一个明确的、由本报告发现驱动的改进方向。
- **单次运行，无随机种子重复**：±0.65 pp 量级的增益尚未做多次重跑的显著性检验。

## 🔁 复现说明

报告中的所有数字均可由配对分析脚本重跑得到。脚本以 SFT 与 GRPO 两份 eval 结果 JSON 为输入，输出整体指标、配对转移（修复/破坏）、按家庭和按字段的拆解，以及全部回退样本：

```bash
python analyze_eval.py <SFT_eval.json> <GRPO_eval.json>
```
